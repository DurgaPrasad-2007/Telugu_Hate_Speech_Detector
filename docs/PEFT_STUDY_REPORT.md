# Parameter-Efficient Adaptation for Telugu Abusive-Comment Detection

Data: pure Telugu MACD files only (`data/telugu_{train,val,test}.csv`; the code-mixed
files were not used). Every number below comes from `results/study/study_results.csv`
and the run folders it points to. Tables are regenerated by `src/aggregate_study.py`
into `results/study/summary.md`.

## 1. Summary

| Question | Answer (evidence) |
|---|---|
| Does LoRA match full fine-tuning? | Yes, within noise. MuRIL, 3 seeds: LoRA 0.9052 ± 0.0030 vs full 0.9049 ± 0.0028 test macro-F1; validation 0.9026 ± 0.0020 vs 0.9035 ± 0.0023. |
| Cost | LoRA trains 296,450 parameters (0.125%) vs 237.6M, and peaks at 1.6 GB vs 4.6 GB GPU memory. |
| Is DoRA better than LoRA? | No clear gain. MuRIL: 0.8984 vs 0.9026 val (LoRA higher, 3 seeds). XLM-R: 0.9027 vs 0.9035 val and 0.9055 vs 0.9035 test (tie, 3 seeds). |
| Is AdaLoRA better? | No. 3 seeds each: XLM-R 0.8891 ± 0.0013 test (LoRA 0.9035), MuRIL 0.8946 ± 0.0003 (LoRA 0.9052); ~1.5 points lower, 2x the training time. |
| Which backbone? | No clear winner. LoRA test macro-F1, 3 seeds: MuRIL 0.9052, XLM-R 0.9035, IndicBERTv2 0.9017 (std ~0.003-0.004). mBERT is lowest at 0.8946. |
| Rank | Weak effect. Alpha matters more: alpha=64 was best at every rank. |
| Learning rate | 2e-4 best; 1e-4 undertrains, 5e-4 degrades (0.844 val). |
| Deployment | Dynamic INT8 ONNX costs 3-4 points of macro-F1 (section 6). The INT8 model previously committed to git is broken (0.37 macro-F1). |

The earlier session's conclusion that "every PEFT method underperformed full fine-tuning by
3-16 points" was an artefact of undertraining (lr 1e-4, 3 epochs, no early stopping), not a
property of the method.

## 2. What the paper did (and what was adopted)

Paper: *Indonesian Hate Speech Detection Across Diverse Domains Using Parameter-Efficient
Fine-Tuning with IndoBERT and LoRA* (Jurnal Minfo Polgan, 2026, doi 10.33395/jmp.v15i2.16581).
Adopted: LoRA on query/value only; grid over rank {4,8,16,32} x alpha {16,32,64}; then
learning rate {1e-4,2e-4,5e-4}; AdamW; FP16; early stopping on validation F1 (patience 3).
Not adopted: back-translation and domain downsampling (not applicable to a single-domain
Telugu set), regex cleaning that strips emoji/punctuation (the repo keeps them),
batch size 8 (we used 16), max length 128 (we used 96).

## 3. Setup

- Hardware: one RTX 4060 Ti 8 GB, Windows 11. Software: torch 2.6 / transformers 4.57.6 / peft 0.21.0.
- Data: 23,980 / 3,000 / 3,000 rows after the repo's existing train-to-val/test leakage filter
  (final eval sets 2,998 val / 2,997 test).
- Max length 96, batch 16, AdamW, weight decay 0.01, cosine schedule, 10% warmup, FP16.
- LoRA family: up to 10 epochs, early stopping patience 3, best checkpoint by validation
  macro-F1. Full fine-tuning: lr 2e-5, up to 5 epochs, same early stopping.
- Selection used validation macro-F1 only. Test is read once per run for reporting; no
  configuration was chosen on it. (Test numbers were visible while choosing, so treat the
  test column as reporting, not as an untouched holdout, in the strict sense.)

## 5. Observations on AdaLoRA

The previous AdaLoRA run collapsed to a constant prediction (0.34 macro-F1). In this study
the training code was changed on three things at once: PEFT's rank-allocation step is now
called each optimizer step, the schedule is derived from the real step count, and the
learning rate/epochs/modules changed. It now trains (0.89). Which change fixed it was not
isolated. It still does not beat plain LoRA here.

## 6. Deployment: quantization findings

Best model by validation: LoRA r=8, alpha=64, seed 42. Merged into the base model and
exported to ONNX (`src/export_best.py`, output in `results/final_lora/`).

| variant | size | val F1 | test F1 |
|---|---|---|---|
| merged fp32 (PyTorch) | ~900 MB | 0.9048 | 0.9081 |
| ONNX fp32 | ~900 MB | 100% agreement with torch (300 val rows) | - |
| INT8, per-tensor weights (the repo's old recipe) | 238 MB | 0.632 | 0.633 |
| INT8, per-channel MatMul, fp32 embeddings | 694 MB | 0.881 | 0.882 |
| INT8, per-channel MatMul + Gather | 239 MB | 0.867 | 0.870 |

- The merge is correct (fp32 reproduces the training score).
- The export is correct (fp32 ONNX matches torch exactly).
- Per-tensor dynamic INT8 breaks the model: it predicts "abusive" for 25% of comments
  instead of 53%.
- **The INT8 model committed under `onnx_model_muril_int8/` uses that same recipe. On a
  600-comment test sample it scores 0.369 macro-F1 and predicts abusive 3% of the time.**
  The previous report said its accuracy "has not been measured"; it is unusable. Do not ship it.
- Latency (this PC, CPU, including tokenization, batch 1, 200 test comments), per-tensor INT8
  recipe, so the timing applies to the same graph size: 1 thread 55 ms median / 79 ms mean;
  4 threads 19 ms median. fp32 PyTorch: about 100 ms median at either thread count. These were
  not measured on a ₹40k-class laptop, which is typically slower than this machine.
- Reasonable laptop options: (a) fp32 ONNX, best accuracy, ~900 MB; (b) per-channel INT8 with
  fp32 embeddings, 694 MB, -2.7 points; (c) per-channel INT8 incl. embeddings, 239 MB,
  -3.8 points. Static INT8 calibration or quantization-aware training were not tried and may
  recover the loss.


### 6b. Final selected model (XLM-R + LoRA r=8, alpha=64): measured deployment variants

Selected by `src/select_best.py` (validation only; `results/study/selection.md`). Export and
evaluation by `src/export_best.py`, output in `results/final_best/`. Same 2,998 val / 2,997 test
comments, max length 96. The INT8 here uses per-channel weights (`export_onnx.py`).

| variant | size | val macro-F1 | test macro-F1 | latency, 1 thread (median) | latency, 4 threads (median) |
|---|---|---|---|---|---|
| fp32 PyTorch (merged) | ~1.1 GB | 0.9073 | 0.9042 | 43.1 ms | 17.9 ms |
| INT8 ONNX, per-channel | 279 MB | 0.8995 | 0.8926 | 23.1 ms | 8.3 ms |

INT8 agrees with fp32 on 96.1% (val) / 96.8% (test) of predictions and costs about 1.2 points of
test macro-F1. Latency includes tokenization, batch size 1, 200 test comments, measured on the
development PC (not a laptop). Peak RAM was not measured. The earlier MuRIL numbers in the
table above are superseded for deployment purposes; the per-tensor recipe in the first INT8
row is the one that must not be used.

## 7. Limitations

- Single dataset, single language; no cross-domain or code-mixed evaluation (intentionally excluded).
- Three seeds; no significance testing. Only LoRA, DoRA and full FT have multiple seeds.
  Rank/alpha/lr grids and mBERT DoRA are single-seed.
- Hyperparameters were tuned on MuRIL with LoRA, then reused for DoRA/AdaLoRA/other
  backbones without their own tuning. This may disadvantage DoRA and AdaLoRA (and XLM-R).
- QLoRA and IA3 were not re-run with the corrected schedule; their old numbers (0.870 /
  0.726) come from the undertrained setup and are not comparable.
- Original `ai4bharat/indic-bert` not evaluated (gated); IndicBERTv2 used instead.
- Training times are contaminated by shared GPU use.
- Test metrics were printed alongside validation for every run.
- No laptop measurement; latency numbers are from the development PC.

Reading it: every XLM-R method except AdaLoRA lands within 0.2 points of full fine-tuning
(0.9035-0.9057), inside the seed spread. LoRA trades recall for precision (abusive recall
0.883 vs 0.905 for full FT, precision 0.929 vs 0.914): if missing abuse is the costlier error,
full FT or DoRA is the safer choice, or lower the decision threshold on LoRA. The adapter is
3.4 MB vs a 1.06 GB full checkpoint (about 300x smaller).

## 8. Recommendations for the next iteration

1. Treat LoRA r=8, alpha=64 (about 1.2 MB of adapter weights vs ~900 MB) as the default;
   it matches full FT at one third of the memory. Per-task adapters are practical.
2. Fix or remove `onnx_model_muril_int8/` and pick a deployment variant from section 6,
   re-measuring on a real target laptop. Try static INT8 with calibration data before
   accepting a 3-point loss.
3. Run 5 seeds for LoRA vs XLM-R DoRA, the only head-to-head where the ordering flips by
   backbone, before claiming either.
4. Tune lr for DoRA/AdaLoRA separately (try 3e-4 / 1e-3 for AdaLoRA, which usually prefers
   higher rates) and run mBERT DoRA and an accessible Indic checkpoint.
5. Replace the repo's `README`/`FINAL_REPORT` "winner" claims once the above is settled.

## 10. Problems encountered (for the log)

- A `json` import bug in the patched `train.py` crashed the first 4 grid runs after
  training; fixed and those runs were discarded and re-run.
- The session restarted mid-grid; the sweep was relaunched and skipped finished runs.
- The default INT8 quantization config silently produced an accurate-looking file that was
  not accurate; found only because INT8 was evaluated against fp32.
